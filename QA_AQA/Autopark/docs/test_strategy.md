## 2. Общие принципы

### 2.1 Принципы тестирования
1. **Раннее тестирование** - тесты создаются параллельно с разработкой
2. **Автоматизация** - критичные и повторяющиеся тесты автоматизированы
3. **Риск-ориентированность** - фокус на критичных бизнес-процессах
4. **Непрерывность** - тесты интегрированы в CI/CD
5. **Изоляция** - тесты независимы и не влияют друг на друга

### 2.2 Уровни тестирования

#### 2.2.1 API/Unit уровень
- Тестирование отдельных эндпоинтов
- Валидация входных/выходных данных
- Проверка бизнес-логики на уровне API

#### 2.2.2 Интеграционный уровень
- Взаимодействие с БД (PostgreSQL)
- Интеграция с Minio (файловое хранилище)
- Интеграция с внешними сервисами (GLONASS)

#### 2.2.3 Системный уровень
- End-to-end сценарии
- Smoke тестирование
- Регрессионное тестирование

## 3. Типы тестирования

### 3.1 Функциональное тестирование

#### 3.1.1 Smoke тесты
**Цель:** Проверка базовой работоспособности системы  
**Покрытие:** Критичные бизнес-потоки  
**Частота:** При каждом коммите/деплое

**Примеры:**
- Авторизация пользователя
- Создание/получение User
- Создание/получение Vehicle
- Healthcheck

**Маркер:** `@pytest.mark.smoke`

#### 3.1.2 Sanity тесты
**Цель:** Быстрая проверка после изменений  
**Покрытие:** Измененный функционал + зависимые модули  
**Частота:** После каждого изменения функционала

#### 3.1.3 Регрессионное тестирование
**Цель:** Проверка отсутствия регрессий  
**Покрытие:** Весь функционал  
**Частота:** Перед релизом, после исправления критичных багов

**Маркер:** Используются стандартные маркеры без специальной пометки

#### 3.1.4 API тестирование
**Цель:** Полное покрытие REST API  
**Покрытие:** Все эндпоинты, методы, статус-коды

**Стратегия:**
- Позитивные тесты (happy path)
- Негативные тесты (invalid input, unauthorized)
- Граничные значения
- Валидация схемы ответов

**Маркер:** `@pytest.mark.api`

### 3.2 Нефункциональное тестирование

#### 3.2.1 Безопасность
**Цель:** Проверка защищенности системы  
**Области:**
- Авторизация и аутентификация
- Валидация входных данных (SQL injection, XSS)
- Защита от несанкционированного доступа
- OWASP Top 10

**Чеклист:** см. `security_checklist.md`

#### 3.2.2 Интеграционное тестирование
**Цель:** Проверка взаимодействия компонентов  
**Области:**
- API ↔ PostgreSQL
- API ↔ Minio
- API ↔ GLONASS (внешний сервис)

**Маркер:** `@pytest.mark.integration`

#### 3.2.3 Производительность
**Цель:** Проверка времени отклика  
**Области:**
- Критичные эндпоинты (login, GET /user, GET /vehicle) - ✅ реализовано
- Массовые операции
- Нагрузочное тестирование - ✅ базовое покрытие реализовано (test_load.py)

**Маркер:** `@pytest.mark.load` (исключены из обычного прогона), `@pytest.mark.slow`

## 4. Подход к тестированию

### 4.1 Пирамида тестирования

```
          / \
         /   \
        /     \
       /  E2E  \        <-- Мало тестов (smoke, критичные сценарии)
      /---------\
     /           \
    / Integration \     <-- Среднее количество
   /---------------\
  /                 \
 /     API Tests     \  <-- Больше всего тестов
/---------------------\
```

### 4.2 Стратегия покрытия

#### Приоритет 1: Критичные бизнес-процессы
- ✅ Авторизация/регистрация (100% покрытие)
- ✅ CRUD User (100% покрытие)
- ✅ CRUD Vehicle (100% покрытие)

#### Приоритет 2: Важные бизнес-процессы
- ✅ Управление заказами (100% покрытие - Driver, Logist, Mechanic Orders)
- ✅ Интеграции (100% покрытие - GLONASS, MinIO, System)

#### Приоритет 3: Вспомогательный функционал
- ✅ Справочники (100% покрытие - User Role, Vehicle Type)
- ✅ Административные функции (100% покрытие - User Group, Payment, Salary, Compensation)

**Текущий статус:** ✅ **100% покрытие всех эндпоинтов из OpenAPI схемы** (105/105 методов)

### 4.3 Подход к позитивному тестированию
1. Happy path сценарии
2. Проверка всех обязательных полей
3. Валидация структуры ответов
4. Проверка бизнес-правил

### 4.4 Подход к негативному тестированию
1. Невалидные входные данные
2. Отсутствующие обязательные поля
3. Неавторизованный доступ
4. Нарушение бизнес-правил (дубликаты, конфликты)
5. Граничные значения

## 5. Тестовые данные

### 5.1 Стратегия управления данными
- **Изоляция:** Каждый тест работает со своими данными
- **Автоочистка:** Фикстуры автоматически удаляют созданные данные
- **Уникальность:** Генерация уникальных email/phone для предотвращения конфликтов

### 5.2 Типы тестовых данных

#### Базовые тестовые пользователи
- Тестовый пользователь для авторизации (из `.env`)
- Временные пользователи (создаются в тестах, удаляются после)

#### Тестовые транспортные средства
- Временные ТС (создаются в тестах, удаляются после)
- Уникальные номера (генерация случайных значений)

### 5.3 Фикстуры и helpers
```python
# Автоматическая очистка
@pytest.fixture
def user_cleanup():
    # Регистрация для удаления после теста
    ...
    
@pytest.fixture
def authenticated_session():
    # Сессия с авторизацией
    ...
```

## 6. Автоматизация

### 6.1 Инструменты
- **Фреймворк:** pytest
- **HTTP клиент:** requests
- **Отчетность:** pytest-html
- **Конфигурация:** pytest.ini, conftest.py

### 6.2 Структура автотестов
```
tests/
├── api/                           # API тесты (100% покрытие)
│   ├── test_auth.py              # Авторизация
│   ├── test_user.py              # Пользователи
│   ├── test_user_*.py            # User расширенное (роли, группы, платежи, зарплаты)
│   ├── test_vehicle.py           # Транспорт
│   ├── test_vehicle_*.py         # Vehicle расширенное (типы, обслуживание, файлы)
│   ├── test_driver_*.py          # Заказы водителей
│   ├── test_logist_order.py      # Заказы логистов
│   ├── test_mechanic_*.py        # Заказы механиков
│   ├── test_report*.py           # Отчёты
│   ├── test_glonass.py           # Интеграция GLONASS
│   ├── test_minio_file.py        # Интеграция MinIO
│   ├── test_system.py            # Системные эндпоинты
│   └── test_load.py              # Нагрузочные тесты
├── ui/                            # UI/E2E тесты
│   ├── pages/                    # Page Object Model
│   └── tests/                    # UI тесты
├── unit/                          # Unit тесты
├── config/                        # Конфигурация
├── conftest.py                    # Фикстуры
└── requirements.txt               # Зависимости
```

### 6.3 Маркировка тестов
- `@pytest.mark.smoke` - критичные тесты
- `@pytest.mark.api` - API тесты
- `@pytest.mark.integration` - интеграционные
- `@pytest.mark.ui` - UI/E2E тесты
- `@pytest.mark.e2e` - сквозные сценарии
- `@pytest.mark.regression` - регрессионные
- `@pytest.mark.load` - нагрузочные (исключены из обычного прогона)
- `@pytest.mark.slow` - долгие тесты
- `@pytest.mark.unit` - unit тесты
- `@pytest.mark.requires_auth` - требующие авторизации
- `@pytest.mark.security` - проверки безопасности

### 6.4 CI/CD интеграция
- Автоматический запуск smoke тестов при коммите
- Полный прогон перед merge в основную ветку
- Автоматическая генерация отчетов

## 7. Окружения

### 7.1 Тестовые окружения

#### DEV
- **Назначение:** Разработка и первоначальное тестирование
- **Доступность:** 24/7
- **Стабильность:** Может быть нестабильным

#### STAGING
- **Назначение:** Полное тестирование перед релизом
- **Доступность:** По требованию
- **Стабильность:** Должно быть стабильным

### 7.2 Управление конфигурацией
- Переменные окружения в `.env`
- Раздельные конфиги для разных окружений
- Секреты хранятся в защищенном месте

## 8. Метрики и отчетность

### 8.1 Ключевые метрики
- **Покрытие тестами:** ✅ **100% эндпоинтов из OpenAPI схемы** (105/105 методов) + 4 не задокументированных
- **Процент пройденных тестов:** Pass rate
- **Стабильность тестов:** % успешных прогонов
- **Время выполнения:** Длительность тестовых прогонов
- **Плотность багов:** 2 известных бага (BUG-USER-EMAIL-VALIDATION, BUG-USER-PHONE-VALIDATION)

### 8.2 Отчетность
- Ежедневный статус тестирования
- Отчеты о багах (по приоритетам)
- Финальный отчет о тестировании перед релизом

## 9. Управление рисками

### 9.1 Риски тестирования
1. **Нестабильность окружения** → Резервные окружения
2. **Изменения в API** → Версионирование API, уведомления
3. **Недостаток тестовых данных** → Автоматическая генерация
4. **Время выполнения тестов** → Параллельный запуск, оптимизация

Подробнее см. `risk_analysis.md`

- ✅ Использование классов для группировки связанных тестов
- ✅ Маркировка тестов для селективного запуска

### 10.3 Поддержка тестов
- ✅ Регулярный рефакторинг
- ✅ Обновление при изменениях в API
